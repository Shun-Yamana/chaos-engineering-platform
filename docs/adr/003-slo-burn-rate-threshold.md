# ADR 003 - SLO バーン率閾値の設計

- Status: Accepted
- Date: 2026-04-27

## Context

カオスエンジニアリング実験の自動停止条件として、SLO 閾値の設計が必要だった。
単純なエラーレート閾値（例：5% 超で停止）だけでは以下の問題がある：

- 瞬間的なスパイクで誤検知する
- エラーバジェットの消費速度を考慮できない

Google SRE ブックで提唱されているバーン率（Burn Rate）アラートを採用することにした。

## Decision

以下の2つの条件を **OR** で評価し、どちらかを超えた場合に実験を自動停止する：

| 閾値 | デフォルト値 | 意味 |
|---|---|---|
| `error_rate_threshold` | 0.05（5%） | 直近1分間のエラーレートが 5% を超えた |
| `burn_rate_threshold` | 2.0 | バーン率が 2 倍を超えた（エラーバジェットを2倍速で消費中） |

## Rationale

### バーン率の定義

```
バーン率 = エラーレート / エラーバジェット消費率
        = エラーレート / (1 - SLO目標値)
```

SLO 目標値 99.9%（エラーバジェット 0.1%）の場合：
- エラーレート 0.1% → バーン率 1.0（正常速度で消費）
- エラーレート 0.2% → バーン率 2.0（2倍速で消費）

### バーン率閾値を 2.0 にした理由

- バーン率 1.0 は「SLO 目標ちょうどの消費速度」であり、実験中は多少の劣化を許容したい
- バーン率 2.0 は「通常の2倍速でエラーバジェットを消費している」状態であり、
  明確にシステムが劣化していると判断できる実用的な境界値
- Google SRE ブックでは 14.4（1時間で月次バジェットを5%消費するレート）を推奨しているが、
  本プロジェクトはデモ用途のため、より敏感な 2.0 を採用してデモ映えを優先した

### エラーレート閾値を 0.05（5%）にした理由

- バーン率だけでは SLO 目標値が低い（例：99%）サービスで感度が低くなるため、
  絶対値での閾値を補完的に設定
- 5% は Web API の一般的な「明らかに異常」と判断できる水準

### OR 条件にした理由

AND 条件にすると両方の条件を同時に満たさないと停止されない。
カオス実験は影響範囲を最小化するべきであり、どちらか一方が危険水準に達した時点で即座に停止する OR 条件が適切。

## Consequences

- バーン率 2.0 は敏感な閾値のため、正常時のノイズで誤検知する可能性がある。
  本番適用時は計測ウィンドウの拡大（5分など）やバーン率閾値の引き上げを検討すること。
- 閾値は DynamoDB の `slo-definitions` テーブルにサービスごとに保存されており、
  コード変更なしで調整可能な設計になっている。
