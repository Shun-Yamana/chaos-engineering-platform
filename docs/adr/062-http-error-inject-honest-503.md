# ADR 062 - http_error_inject（a→b）は 503 を素直に返す — フォールバック不採用

- Status: Accepted
- Date: 2026-05-23

## Context

⑤ http_error_inject（a→b パスへの Envoy abort filter 注入）に対して、インフラ層の防衛策がゼロであることが確認された（ADR 061）。この状態で service-a の SLO が違反するため、アプリ層のフォールバック（キャッシュ・デフォルト値返却）を追加すべきかを検討した。

## Decision

service-a は service-b が 5xx を返した場合でも**フォールバックを実装しない。503 をそのまま上流に返す。**

## Rationale

service-b（products）はクリティカルパスであり、その応答なしに意味のあるレスポンスを返すことができない。

- キャッシュを返す場合: 古い商品情報を「正常」として提供することになり、呼び出し元が誤った情報を使って処理を続けるリスクがある
- デフォルト値を返す場合: 「データなし」と「サービス障害」の区別が呼び出し元でつかなくなる

b が完全に機能していない状態で 200 を返すことは、障害を隠蔽することになる。呼び出し元（JMeter / フロントエンド）が障害を認識できるよう、503 を素直に返して「今この API は使えない」を正直に伝える方が正しい。

### c との対比

| パス | b / c の性質 | フォールバック |
|---|---|---|
| ⑤ a→b（http_error_inject） | クリティカル（商品情報） | **なし。503 を返す** |
| ⑩ b→c（http_error_inject） | 非クリティカル（レビュー） | あり（reviews=null で 200） |

c（reviews）は「なくても商品は表示できる」が、b（products）は「なければ何も返せない」。

## Consequences

- ⑤ 実験中は service-a の SLO が違反し続ける（エラー率 ~100%）
- CloudWatch アラーム発火 → emergency_stop が唯一の自動回復手段
- フォールバックを持たないことで、実験が「b への依存の強さ」を正直に可視化する
- アプリ層の防衛設計として追加するものはない。⑤ に対する防衛は emergency_stop のみ
