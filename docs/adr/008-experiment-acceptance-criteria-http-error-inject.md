# ADR 008 - 実験合格基準：http_error_inject

- Status: Accepted
- Date: 2026-04-30

## Context

http_error_inject 実験の合格基準を定義するにあたり、他の実験（pod_kill / cpu_stress / memory_stress）との性質の違いを明確にする必要があった。

他の実験は「障害が起きても SLO 内に収まるか（耐える）」を検証するのに対し、http_error_inject は意図的に SLO 違反を引き起こし、「検知・停止・通知のパイプラインが正しく機能するか」を検証する実験である。

合格基準を設計するにあたり、「ギリギリの SLO 違反（fault_rate=0.1）を検知できるか」と「確実な違反（fault_rate=0.5）で検知パイプラインをE2E検証するか」の2方針を検討した。

## Decision

fault_rate=0.5（50%エラー）を使用し、合格基準を「検知→自動停止→通知」のパイプラインが確実に動作することに置く。

| 指標 | 合格基準 |
|------|---------|
| SLI 検知 | 5分以内（WINDOW_MINUTES）にエラーレート上昇を記録 |
| auto-stopper 発動 | バーンレート閾値超過で実験を自動停止 |
| Slack 通知 | auto-stopper 発動と同時に通知が届く |
| 回復 | FAULT_RATE 除去後、エラーレートが SLO 閾値（5%）以内に戻る |

## Rationale

### fault_rate=0.1（ギリギリ検知テスト）を外した理由

SLO 閾値（5%）をわずかに超える fault_rate=0.1 での検知テストは、バーンレートアラートの感度調整には有用だが、この実験の主目的ではない。境界値での検知精度より、パイプライン全体が動くことの確認を優先した。

### fault_rate=0.5（E2E パイプライン検証）を採用した理由

実運用の設計思想として「SLO を厳密に違反してから検知するのではなく、実害が出る前に止める」ことを重視している（ADR 003 のバーンレート閾値採用と同じ思想）。fault_rate=0.5 は確実にバーンレート閾値を超えるため、検知→停止→通知の一連のパイプラインを確実に動かしてE2E検証できる。

ただしアラートのノイズ化を避けるため、fault_rate を必要以上に高くすることはしない。0.5 は「確実に検知される」かつ「現実的な障害シナリオとして説明できる」値として妥当。

### この実験の位置づけ

```
pod_kill / cpu_stress / memory_stress : 障害耐性のテスト（SLO 内に収まるか）
http_error_inject                     : 検知パイプラインのE2Eテスト（SLO 違反を正しく検知・停止できるか）
```

## Consequences

- http_error_inject は「壊れたことを正しく検知できるか」を検証するため、SLI calculator・auto-stopper・Slack 通知の3コンポーネントが全て正常動作していることが前提になる
- いずれかのコンポーネントが未動作の場合、この実験は合格基準を満たせない（インフラ構築後に実施すること）
- fault_rate=0.1 での感度テストは将来の拡張として残る
