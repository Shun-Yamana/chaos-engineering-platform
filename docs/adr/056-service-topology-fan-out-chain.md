# ADR 056 - サービストポロジー設計: a → { b → c, d } ファンアウト＋チェーン

- Status: Accepted
- Date: 2026-05-22

## Context

当初のサービス構成は service-a / service-b の2サービスのみで、カオス実験のターゲットが実質 service-b 一本だった。
これでは以下の問題がある:

1. **障害の伝播パターンが単純すぎる**: b が死ぬ → a がフォールバック、という1段の依存関係しか表現できない
2. **X-Ray サービスマップが貧弱**: a → b の2ノードだけでは分散トレーシングの価値を示しにくい
3. **レジリエンスパターンの多様性がない**: 全サービスが同じ「直列呼び出し＋フォールバック」になりがち

## Decision

service-c（レビュー要約）と service-d（リアルタイム在庫・価格）を追加し、以下のトポロジーを採用する:

```
service-a ──asyncio.gather──→ service-b ──→ service-c
                          └──→ service-d
```

- **a → b → c（直列チェーン）**: service-b が商品詳細を返す際に service-c からレビュー要約を取得してエンリッチする
- **a → d（並行呼び出し）**: service-a が商品詳細（b）と在庫・価格（d）を `asyncio.gather` で同時取得する

## Rationale

### なぜ「直列チェーン＋ファンアウト」を組み合わせたか

**直列チェーン（b → c）が示すもの:**
- カスケード障害の伝播: c が死ぬと b が部分劣化し、a はレビューなし商品を受け取る
- サービス間でのバルクヘッド: c の障害は b 内部で吸収され、a には伝わらない
- タイムアウト設計の違い: c への呼び出しは 100ms（非クリティカルなため短く設定）

**ファンアウト（a → {b, d}）が示すもの:**
- 独立した劣化: b が遅延していても d は応答し、d が死んでいても b のレスポンスは返る
- レスポンスタイム = max(b, d)（直列なら b + d）という設計上の利点
- サーキットブレーカーを依存ごとに独立して管理（_product_cb / _inventory_cb）

**2パターンを共存させた理由:**
- 単一パターンだけでは「このシステムは1種類の障害しか考慮していない」と見られるリスクがある
- 面接・レビューの場で「なぜ c は b から呼ぶのか」「なぜ d は a から呼ぶのか」を説明できる設計にするため、役割に応じてパターンを使い分けた
  - c（レビュー要約）は商品詳細の一部であり、b が責任を持つ
  - d（在庫・価格）は商品詳細とは独立したリアルタイムデータであり、a が集約する

### なぜ service-c は service-b の非クリティカル依存にしたか

- レビュー要約はページ表示には必須でない（商品名・価格・写真があれば購買判断はできる）
- b が c に強依存すると、c の障害が b を完全停止させ、a のスタックキャッシュが意味を失う
- 100ms タイムアウトは「b のレスポンスタイム目標（200ms）を超えさせない」ための上限

### なぜ service-d は service-a の非クリティカル依存にしたか

- 在庫・価格情報はリアルタイム性が要求されるが、在庫切れの商品を「在庫なし」と表示できなくても致命的ではない
- service-a のサーキットブレーカー（_inventory_cb）が独立しており、d の障害が b への呼び出しパスに影響しない
- FAIL_THRESH=3（service-b の 5 より小さい）: d は非クリティカルなので早めに CB を開いてタイムアウト待ちを避ける

### 単純な3直列（a → b → c）を選ばなかった理由

- 3直列では「a がレイテンシの全合計を受ける」構造になり、c の障害影響が大きすぎる
- ファンアウトの並行実行パターンを示す機会がなくなる
- X-Ray サービスマップとしても a → b → c の線形より a → {b→c, d} のグラフの方が視覚的に分かりやすい

## Consequences

- ✅ X-Ray サービスマップに4ノード（a / b / c / d）が表示され、ファンアウト＋チェーン構造が可視化される
- ✅ カオス実験のバリエーションが増える（c kill → レビュー欠落 / d kill → 在庫情報欠落 / b kill → スタックキャッシュ発動）
- ✅ 2種類のレジリエンスパターン（CB+スタックキャッシュ vs シンプルタイムアウトフォールバック）が実装に混在し、設計の厚みが増す
- ✅ `asyncio.gather` によりレスポンスタイム = max(b, d) となり、d の遅延が b に影響しないことが実証できる
- ⚠️ service-c / service-d の Deployment が追加されるため、EKS ノードの Pod 収容数に余裕が必要（t3.medium × 2 で 8 Pod まで、replicas=2 × 4 サービスで合計 8 Pod ちょうど）
- ⚠️ `_inventory_cb._FAIL_THRESH = 3` はインスタンス属性への直接代入であり、将来 _CircuitBreaker のコンストラクタ引数化を検討すること
